# Agent 任务书

把用户意图变成能力强的执行 agent 能自主完成的任务。规定结果、真实约束和验收，给实现方法留空间；任务书不取代用户后续指令、项目事实源或 harness 权限。

## 工作方式

1. 从请求、现有文件和环境核实目标、范围、必要基线。只运行与验收相关的命令；行业或产品当前事实需要时再联网。未能核实的内容标明假设或待测，不编命令和数字。
2. 信息足够就写任务书。只有方向、验收、权限或费用上的关键未知才集中询问，不固定访谈轮次或问题数量；可逆实现细节选默认值并写明。用户不在场不能代批费用、外发、范围变更或作者事实。
3. 用 [references/anatomy.md](references/anatomy.md) 按需要组织内容。默认直接在聊天中给一个可复制代码块；用户要求落盘才保存。≤4000 字符是本 Skill 的简洁目标，不宣称是当前平台硬限制；不能为凑字数省略必要边界或拆掉用户要的完整目标。
4. 用户只要任务书时，交付任务书即完成，不自行启动 Goal、新任务或执行项目。用户也明确要求执行时，使用实际可用能力继续；不要求用户另发一次启动口令。

## 核心约束

- **目标与方法分开**：用户指定的方法先按约束理解；发现方法不适合时给出证据与建议，未经授权不静默替换重要产品、架构或费用方案。普通实现细节可自行选择。
- **范围具体**：指出可改路径、应保留的不变量及真正禁区。项目已有设计、schema、测试可引用，不重复抄整份。不要一律冻结测试/CI；实现变更需要更新预期时保持业务正确性，不通过削弱检查制造通过。
- **验收关注行为**：任务成功由用户要的结果和必要检查决定，不用测试数量、覆盖率、来源条数或零 skipped 替代业务正确性。只在这些指标本身是需求时设阈值。视觉或研究结果使用可观察的审阅标准，不强行变成机器评分。
- **自主完成**：基线漂移先核实影响，能在原范围内处理就修正并继续；关键前提失效才阻塞依赖部分。反复失败应改变方法；不要“失败三次换项”或“跑满轮次即完成”。预算/期限只有用户约定或实际资源限制时才成为停止条件。
- **真实状态**：完成、部分完成、阻塞明确区分。允许以证据说明探索方向不可行；不能把执行项目没做成包装成合格交付。
- **接力按需**：长任务沿用 `PROGRESS.md`、`DESIGN.md`；阻塞记录在已有状态文件，不额外强制 `BLOCKED.md`、开工回执和空模板。状态更新在里程碑、关键变化和结束前进行。

## 验证与并行

执行 agent 负责自测与证据。只有复杂、高风险或容易自证的任务才安排独立复核；复核人使用独立样例和原始材料，不伪造“暗卷”或声称未实际运行的独立验收。故障注入仅用于需要验证报警/失败检测机制的任务，在隔离环境进行。

用户要求拆并行任务时，明确各自输入、输出、文件所有权、接口与统一验收。日常有界委派遵守 AGENTS 的成本边界；已授权无需再问“是否允许拆”。允许原范围内的接口协调，禁止回退他人改动。不能独立推进的任务由主 agent 连续执行。

## 交付

用一句说明任务书用途，给一个可复制块；只列实际待决定或未验证的关键事项。根据目标工具是否支持 Goal 给出准确用法，不臆造命令。语言简明；可选风格见 [references/style.md](references/style.md)，只在用户明确需要时读取。
