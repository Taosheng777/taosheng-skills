# Teach

把真实问题转化为一次短而完整的学习循环。以用户展示出的理解为掌握证据，不把“讲过”当成“学会”。

## 1. 判断教学任务

先识别用户真正要获得的能力：临床推理、沟通技术、科研方法、证书知识或其他可迁移技能。把项目执行、投稿修改、行政事项和投资决策交给对应工作流；只有用户明确要学习其底层能力时，才进入教学。

优先从用户正在处理的病例推演、跟诊反思、研究设计、课程教材或既有文章中选取问题。避免为了完整而铺设通用课程体系。

## 2. 取得上下文与证据

读取用户提供的材料，以及当前项目已有的 `PROGRESS.md`、`DESIGN.md` 和必要的 `PLAN.md`。处理用户个人 Obsidian、工作目标或医学学习时，读取 [个人学习工作流](references/personal-learning-workflow.md)。

先找高可信来源，再讲授事实。医学与科研主题优先使用现行指南、系统综述和原始研究；工具主题优先使用官方文档与源代码。把个人经历和病例当作学习情境，不当作一般结论的证据。

对需要联网核实的短课，在第一次事实反馈前建立一组小型来源基线，后续回合复用。只有教学问题改变、来源不足或事实可能更新时才继续搜索；不要每轮重复检索相同概念。

首次使用敏感医学资料时，提醒资料类型、教学用途和处理去向，然后继续。真实外发仍等待用户明确确认。

## 3. 决定是否建立状态

- 单次短课：默认只在对话中完成，不创建文件。
- 明确要跨会话继续：先确认学习工作台位置，再建立最小状态。
- 已有工作台：先读 `PROGRESS.md`，再读 `DESIGN.md`，从记录的下一课继续。

多会话工作台只使用：

```text
学习主题/
├── DESIGN.md
├── PROGRESS.md
├── work/       # 有原始材料时才建
└── outputs/    # 确有可读交付物时才建
```

使用 reference 中的最小格式。不要另建 `MISSION.md`、`RESOURCES.md`、`NOTES.md`、`learning-records/` 或强制复习日历。

## 4. 运行一节短课

每次只推进一个能在约 10–20 分钟内完成的能力目标：

1. 用一句话说明本课目标及完成标准，让用户知道本课只练什么。
2. 在讲解前给出一个问题、病例或任务，让用户先回答；一次只要求一个聚焦输出。
3. 等待用户作答，保留其原判断和推理顺序；评价内容，不把句数或排版服从度当作能力证据，除非格式本身就是学习目标。
4. 先指出正确部分，再定位一个最重要的误区或缺口。用户提出相邻但有效的问题时先承认其价值，再带回本课目标。
5. 区分可观察事实或数据、解释或假设、以及能够据此采取的判断；用来源基线解释原因、边界和不确定性。
6. 改变一个关键条件做迁移练习，再等待回答。必要时最多再给一次聚焦迁移，不把短课拖成整章课程。
7. 根据用户表现标记掌握层级：
   - `未展示`：尚未独立说出关键判断。
   - `初步识别`：能在原情境中识别概念，但仍依赖提示或混淆边界。
   - `已迁移`：能在变化后的情境中正确应用，并说出不能据此推断什么。

优先使用开放回忆、病例推演、口述思路、比较判断和真实任务演练。不要用答案长度、排版或明显提示泄露正确选项。

## 5. 记录进展

多会话课程结束一课后，只在 `PROGRESS.md` 更新：

- 已展示的掌握层级和具体证据
- 仍存在的误区或待核实项
- 下一课的一个自然问题
- 本课实际使用的关键来源

材料仅被讲过、读过或浏览过时，不记录为掌握。不要生成逐次活动日志，也不要制定未经用户要求的日历排期。

## 6. 交付与沉淀

默认在对话中交付本课反馈。只有图示、交互练习或长内容确实提升学习时，才在工作台 `outputs/` 生成 HTML；不要为每课强制建文件。

Obsidian 是精选沉淀层，不是课程状态层。用户明确要求写入后，才把一个已经形成中心认识的学习单元整理为一篇可读文章；保留用户原回答、认识变化、证据边界和生活或工作连接，不自动拆成知识卡、来源笔记或主题地图。

## 7. 收尾

用三项结束本课：

1. 用户现在已经能做什么。
2. 仍不能据此做什么。
3. 下次最值得练的一个问题。

如果来源不足、风险过高或真实工作环境无法验证，明确说明缺口，不用流畅解释掩盖不确定性。
